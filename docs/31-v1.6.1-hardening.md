# V1.6.1 hardening: the six "Assembler" issues, mapped to this repository

The V1.6.1 task list (A1–A6) was written against the standalone **Aureon Trading Bot V1.6**
(`assembler/app.py`, `aureon/db.py`, `deploy/autopull.sh`, `scripts/verify_e2e.sh`). None of
those files exist here. This repository stays the central agent-orchestration and API
platform; the V1.6 bot keeps its own risk engine and talks to Assembler only through
authenticated APIs (today: `POST /api/trading/mt5/ingest`). Nothing below merges the bot in or
duplicates its risk engine, and no strategy (EMA/VWAP or other) or live-trading path changed.

Each issue was mapped to the component that actually plays that role here, fixed only where an
equivalent defect exists, and covered by regression tests that **fail on the V1.6 code**.

### A1: the kill switch could be released by accident

*Did the architecture need a new persistent risk lock?* No. `risk_policies.kill_switch` is a
Postgres column (survives restarts), enforced by the risk checks of research signals and paper
intents (`kill_switch_off`). No new table or state machine was added.

*Defect:* `RiskPolicyIn.kill_switch` defaulted to `false`, so any PUT that omitted it (a client
editing only limits) **silently released an engaged kill switch**; the PUT was also a blind
read-modify-write (two admins: last write wins, a stale form undoes a lock set meanwhile), and
two first PUTs raced into a unique-violation 500.

*Fix:* the policy row is locked (`SELECT … FOR UPDATE`) for the read-check-write; an omitted
`kill_switch` keeps the stored value; optional `expected_updated_at` (the `updated_at` the
caller read) gives optimistic concurrency (409 `stale_policy`); **releasing** an engaged kill
switch (true → false) requires `expected_updated_at` (409 `kill_switch_release_needs_version`
otherwise). Engaging never needs it. The account-mode change also locks the account row.

### A2: one value must never be two credentials

The ingest route already compared the bearer in constant time and the token grants nothing
else. *Defects:* (1) nothing stopped `MT5_INGEST_TOKEN` from equalling `MT5_STATUS_TOKEN`,
which the API **sends** to the bot's `/status` URL, so whoever reads that outbound request
could push as the bot (or another credential, e.g. `SECRET_KEY`, `GITHUB_WEBHOOK_SECRET`);
(2) the ≥ 32-char rule ran only at prod startup, but the token can be changed at runtime as a
managed setting (the settings "test" button even accepted 24 chars).

*Fix:* one shared check (`app/core/prod_checks.py`): strength (≥ 32, no placeholder) + no
reuse of `MT5_STATUS_TOKEN`, `SECRET_KEY`, `GITHUB_WEBHOOK_SECRET`, `GITHUB_TOKEN`,
`SETTINGS_MASTER_KEY`. Applied at prod startup, on every ingest request (reuse in any env,
weakness in prod → 503 `ingest_misconfigured`, fail closed), on managed-settings writes (422)
and in the settings test. A bad or missing bearer stays **401** (the existing bot contract);
403 is used where a valid session lacks a role, as before. A role × endpoint matrix test pins
that the bot token opens no session route and no other credential opens ingest.

### A3: a 2xx was enough to promote a release

`deploy.sh` promoted after one `curl -f` success and never read the body; a proxy page or a
half-started app could pass. *Fix:* a pass is HTTP 200 **and** `{"status": "ready"}` with every
check `ok: true`, required twice in a row; the last-good marker is only written for a promoted
release; exit 1 = rolled back healthy, **exit 2 = rollback unhealthy**, and `deploy-poll.sh`
records "rolled back" only for exit 1 (it used to claim a rollback even when it failed).

### A4: verify the schema, not alembic's exit code

`python -m app.workers.migrate --check` (read-only) reads `public.aureon_alembic_version` and
compares it with the image's revision scripts: `at_head` (exit 0), `pending` (exit 3, lists the
revisions upgrade would apply; also a never-migrated database), `diverged` (exit 4: a recorded
revision this build lacks, or several heads), `unreachable` (exit 1). Postgres runs each upgrade
in one transaction, so a failed upgrade leaves the last good revision and shows as `pending`,
never half-applied. `migrate` (the compose one-shot) now verifies head after upgrading, and
`deploy.sh` runs `--check` before starting the new release.

**Real defect found while testing:** migration `0024` passed the bare name
`ck_incidents_source` to `drop_constraint`, which the naming convention turned into
`ck_incidents_ck_incidents_source`; `alembic upgrade head` **failed on every database** that came
through `0016`. Fixed with `op.f()`. Editing the released file is safe: the old version cannot
have succeeded on any database built by these migrations, so no database records `0024` from it.

**Second defect, same cause (downgrade only):** `0020` created `ai.conversations`' provider check
with a bare name, so its real name is `ck_conversations_ck_conversations_provider`; `0023`'s
downgrade re-added it with raw SQL as `ck_conversations_provider`, so `0020`'s downgrade (and
`alembic downgrade base`, the rollback drill and the restore drill's chain) failed. `0023`'s
downgrade now spells the real name. Upgrade paths and existing constraint names are unchanged. See "Integration requirements" for the production server.

### A5: the scheduler could overwrite a cancel

Cancel and the approval executor already locked the intent row. *Defect:* the scheduler
(`paper.process_open`) read open intents **without a lock** and then filled/expired them, so a
cancel committed in between was overwritten (reproduced on V1.6: the cancel answered 200, the
intent ended FILLED with an execution). *Fix:*

- the scheduler locks each intent (`FOR UPDATE SKIP LOCKED`, re-read) and skips rows another
  transaction holds;
- every status change goes through `paper.transition()` with an explicit table
  (PENDING_RISK → REJECTED/APPROVED/CANCELLED/EXPIRED; APPROVED → SUBMITTED/FILLED/CANCELLED/
  EXPIRED; SUBMITTED → FILLED/CANCELLED/EXPIRED; terminal states have no exit), 409
  `invalid_transition` otherwise;
- **compare-and-set without a schema change:** `OrderIntent` maps `status` as its SQLAlchemy
  version column (`version_id_generator=False`), so every ORM UPDATE carries
  `WHERE status = <status read>`; a stale writer gets `StaleDataError` → 409 `conflict`;
- cancel and approve accept an optional `expected_status` (409 `status_mismatch` with the
  current status).

`expected_status` is optional, not required: requiring it would break every existing client,
and the row lock + compare-and-set already make the server-side transition atomic.

### A6: an alert silenced for an hour after a crash

*Did the architecture need an alert queue with leases?* No. Alerts are derived from current
state every 5 minutes (incidents, heartbeats, backups, approvals, Dhan session); there is no
outbox or `SENDING` row to recover. The GitHub webhook queue already recovers (row lock inside
the transaction: a crash rolls back to `pending`, bounded backoff, `failed` after N attempts).

*Equivalent defect:* the dedup key (60 min) was set **before** sending; if the scheduler's
timeout cancelled a hung Discord call (`CancelledError` is not an `Exception`) or the worker
died, the key was never released and the alert was silenced for the whole window. *Fix:* a
short delivery lease (`lease_seconds`: every Discord attempt + backoff + 30 s) with a fencing
token; success turns it into the dedup window, failure releases it, cancellation releases it
(shielded), a crash lets it expire. Commit/release are atomic Redis scripts that only act for
the token holder, so a stale worker cannot clobber a newer attempt. Delivery is at-least-once
(Discord webhooks have no idempotency key): a crash after Discord accepted but before the
commit resends once the lease expires. Retries stay bounded: Discord attempts per run
(`DISCORD_MAX_ATTEMPTS`, exponential backoff, capped 429 waits), then the next 5-minute run.

## API compatibility

| Change | Compatible? |
|---|---|
| `PUT …/risk-policy`: `kill_switch` omitted now keeps the stored value (was: false) | Safer default; clients that always send it see no change |
| `PUT …/risk-policy`: releasing an engaged kill switch needs `expected_updated_at` | **Documented compatibility change** (409 otherwise). Copy `updated_at` from GET. Fails safe: the switch stays engaged |
| `PUT …/risk-policy`: optional `expected_updated_at`, 409 `stale_policy` | Additive |
| `POST …/order-intents/{id}/cancel` / `approve`: optional `expected_status`, 409 `status_mismatch` | Additive (body-less cancel still works) |
| 409 `invalid_transition` / `conflict` on intents | New codes on an existing 409 status |
| `POST /api/trading/mt5/ingest`: 503 `ingest_misconfigured` | Only when the token is reused (any env) or weak (prod) |
| Managed setting `MT5_INGEST_TOKEN`: < 32 chars or reused → 422 | Tightened |
| `deploy.sh` exit 2 | New code; `deploy-poll.sh` updated |

No table, column, index or constraint was added or removed; the only migration changes are the
`0024` constraint-name fix and the `0023` downgrade name fix. Postgres stays reachable only from the compose network and the
roles in `deploy/sql/roles.sql`; no port, volume or compose network changed.

## Coordination with the standalone V1.6 bot

1. **Distinct tokens.** The bot's push token (`MT5_INGEST_TOKEN` here) and its `/status` token
   (`MT5_STATUS_TOKEN` here) must be different values (≥ 32 chars). If they are equal today,
   ingest answers 503 `ingest_misconfigured` after this deploy until one is rotated.
2. **Status codes.** Ingest still answers 401 for a bad token, 503 for disabled/misconfigured;
   the bot should treat 503 `ingest_misconfigured` like `ingest_disabled` (retry later, alert).
3. **Risk.** The bot's own risk lock stays in the bot. Assembler's kill switch governs only
   Assembler-side paper intents and research signals; nothing here pushes it to the bot.

  `expected_status` on cancel/approve.

## Proposed, not implemented

- Readiness check for migration state (`/api/health/ready` reporting `migrations: pending`):
  changes readiness semantics for every consumer; the deploy already gates on `--check`.
- A durable alert outbox (table + leases) if alerts ever carry one-off events that cannot be
  re-derived from state.
- A dedicated `version` integer column on `order_intents` / `risk_policies` (a migration) if
  clients need an opaque ETag rather than `status` / `updated_at`.
- Cross-run exponential backoff for persistently failing Discord deliveries (today: per-run
  retries, then every run).
- A Bot ↔ Assembler risk-lock signal API (one-way, authenticated) if the operators want the
  bot's lock visible in Assembler.
